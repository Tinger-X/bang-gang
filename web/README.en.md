# BangGang Website (web/)

The official site for BangGang: a static site plus Cloudflare Pages Functions.
Live at https://bang-gang.tin.edu.kg

Source repository: https://github.com/Tinger-X/bang-gang

## Layout

```
web/
├── index.html            # single page
├── assets/
│   ├── styles.css        # colours come from the app's own palette
│   ├── script.js         # i18n / theme / comparison slider / download stats
│   ├── logo.png          # app icon (generated by tools/make-logo.ps1)
│   ├── apple-touch-icon.png / favicon-32.png / favicon.svg
│   └── demo/             # comparison screenshots, see "Comparison screenshots"
├── functions/            # Pages Functions
│   ├── download.js       # /download?variant=…: count, then stream the installer from R2
│   ├── api/stats.js      # /api/stats: download counts and version
│   └── _lib/
│       ├── site.js       # ★ site config (app id / repo / variants)
│       └── artifact.js   # artifact key and version parsing
├── tools/
│   ├── publish-artifacts.ps1    # upload dist/installer/ builds into R2
│   └── prepare-demo-shots.ps1   # raw screenshots -> page-ready comparison images
├── schema.sql            # shared D1 schema (account-level, already applied, kept for reference)
├── _headers              # security headers + long cache for /assets/*
├── robots.txt / sitemap.xml
├── wrangler.jsonc        # deploy config (committed)
```

## Shared resources (account-level, reused by every software site)

| Resource | Name | Purpose |
|---|---|---|
| Pages | `banggang` (domain `bang-gang.tin.edu.kg`) | this site |
| D1 | `softwares`, table `counters(app, key, value)` | download counters, isolated by the `app` column |
| R2 | `softwares`, key `<app>/<variant>.<ext>` | release artifacts, isolated by directory prefix |

What this project occupies:

- D1: rows with `app = 'banggang'` — `direct_with_runtime` / `direct_without_runtime` /
  `github` / `github_updated_at`
- R2: `banggang/with-runtime.exe`, `banggang/without-runtime.exe`

> **Do not create a database or bucket for this project.** The shared resources are reused
> across the whole account, and `schema.sql` only ever needs to run once.

## The two installers (variants)

BangGang ships two artifacts: functionally identical, differing only in how the .NET runtime
is packaged. The sibling project (liangbuliang) has one artifact per software; here that
becomes a list — but **every variant still lives under the `<app>/` prefix**, so the shared
bucket's isolation convention holds.

| variant id | R2 key | D1 counter key | Installer |
|---|---|---|---|
| `with-runtime` | `banggang/with-runtime.exe` | `direct_with_runtime` | `BangGang-Setup-<version>-with-runtime.exe` |
| `without-runtime` | `banggang/without-runtime.exe` | `direct_without_runtime` | `BangGang-Setup-<version>-without-runtime.exe` |

The list lives in `SITE.variants` in `functions/_lib/site.js`. **Adding a variant is one array
entry** — the page and the API both read from there.

## Requirements

- Node.js + wrangler (`npm install -g wrangler`)
- Logged in: `wrangler login`

## First-time setup

`wrangler.jsonc` is in the repository with the shared `database_id` / `bucket_name` already
filled in. Normally there is nothing to change: clone it, `wrangler login`, and go.

> It is committed because there is nothing in it worth hiding. The `database_id` is only a
> resource identifier — on its own it grants access to nothing (that needs account
> credentials), and the bucket name already ships inside the deployed artifact anyway. Keeping
> a separate "example" for everyone to copy just means the two copies drift.

## Local development

From inside `web/`:

```bash
wrangler pages dev --port 8787
```

Then open http://127.0.0.1:8787

> Local D1 / R2 are empty local simulations, so `/api/stats` returns 500 and `/download`
> returns 404. To exercise both locally, create the table and put one installer in the local
> bucket first:
>
> ```bash
> wrangler d1 execute softwares --local --file=schema.sql
> wrangler r2 object put softwares/banggang/without-runtime.exe \
>   --file ../dist/installer/BangGang-Setup-0.9.17-without-runtime.exe --local \
>   --content-type application/vnd.microsoft.portable-executable \
>   --content-disposition 'attachment; filename="BangGang-Setup-0.9.17-without-runtime.exe"'
> ```

## Deploy

From inside `web/` (wrangler reads `./wrangler.jsonc` and `./functions/`):

```bash
wrangler pages deploy --project-name=banggang
```

The custom domain `bang-gang.tin.edu.kg` is already bound to the Pages project and does not
need re-binding. (To create a binding, note that wrangler has no subcommand for it — use
`POST /accounts/{account_id}/pages/projects/banggang/domains`. The **DNS record is not created
automatically**: `verification_data` stays at `CNAME record not set` until you add a CNAME from
`bang-gang` to `banggang.pages.dev` (proxied) yourself.)

> **Everything under `web/` is published.** `wrangler pages deploy` uploads the whole
> directory, and `.assetsignore` **does not work on the `wrangler pages deploy` path**
> (measured: the files were uploaded anyway, and the ignore file itself went up as a static
> file). So `https://<domain>/README.md`, `/schema.sql`, `/wrangler.jsonc` and `/tools/*.ps1`
> really do exist. This is not a leak — the same content is in the public repository, and the
> `database_id` in `wrangler.jsonc` is only a resource identifier —
> but it is not obvious, so it is written down here for whoever assumes the deploy directory is
> clean. Cleaning it up properly would mean copying the site into a staging directory before
> deploying; that is not worth it for the benefit, and a `functions/_middleware.js` that 404s
> those paths is the alternative if you ever want it.


## Updating

### Publishing a new version

1. Build the installers: `powershell -ExecutionPolicy Bypass -File tools\build-installer.ps1`
2. Publish them: `powershell -ExecutionPolicy Bypass -File web\tools\publish-artifacts.ps1`

Step 2 overwrites the fixed keys (`banggang/<variant>.exe`) with fresh
`Content-Disposition` metadata. **The version number and download filename exist only in that
R2 object metadata** — once it is overwritten, `/api/stats` and the version labels on the page
follow automatically, with no code change.

The script reads the version from `BangGang.csproj` and the variant list from `site.js`, so
the two cannot drift. `-DryRun` shows what it would do without uploading.

### Updating js / css (cache busting)

`assets/*` is served with `Cache-Control: immutable` (one year) by `_headers`. After changing
one you **must** bump the matching `?v=xxx` in `index.html`, or users keep the old file:

```html
<link rel="stylesheet" href="/assets/styles.css?v=260920001" />
<script src="/assets/script.js?v=260920001"></script>
```

> Everything under `assets/` (including `logo.png` and `favicon.svg`) is immutable —
> any change needs a new version query or a new filename.

### Changing the icon

`assets/logo.png` and friends are generated from `assets/icon-char.png` by
`tools/make-logo.ps1`:

```powershell
powershell -ExecutionPolicy Bypass -File tools\make-logo.ps1
```

Same source and same rule as `app.ico`: never hand-edit the generated PNGs.

## Comparison screenshots (the demo section)

The demo section on the landing page is a **draggable vertical divider**. Both sides are the
same machine at the same moment: on the left "your screen" (BangGang window present), on the
right "what the audience sees" (the frame screen capture receives).

Each scenario needs a pair, placed in `web/assets/demo/`:

```
<scenario id>-visible.jpg   what the machine's user sees
<scenario id>-capture.jpg   what capture receives (same desktop, no BangGang)
```

Scenario ids come from `DEMO_GROUPS` at the top of `assets/script.js`. There are four:
`01` (first launch) / `02` (settings panel) / `03` (asking mid-stream) /
`04` (math and layout). The id is just a key — the display title and caption live in
`DEMO_GROUPS`.

**How to shoot them:**

1. Put the raw screenshots in `shoots/demo/<id>-visible.png` and `<id>-capture.png`
   (`shoots/` is gitignored — local scratch only)
2. Run `powershell -ExecutionPolicy Bypass -File web\tools\prepare-demo-shots.ps1`,
   which writes the page-ready images into `web/assets/demo/`

Where the two frames come from (`tools/run-capture-enabled.ps1` is exactly this switch):

- **visible**: a Debug build with `BANGGANG_SHOW_IN_CAPTURE=1`. This is the only "let capture
  see it" hatch that exists, and it exists only in Debug; Release has no runtime switch at all.
- **capture**: the same scene launched without that variable (or just the Release build).

Apart from the BangGang window itself, the two frames **must be identical** — wallpaper,
background windows, window position and size. The window is `CenterScreen` at 1200×800 and
its position is never persisted, so it lands in the same spot on every launch and the pair
lines up pixel for pixel.

> Only scenarios with both files present appear on the page, so you can fill them in over
> time. With none at all, **the whole demo section and its nav entry are hidden** — production
> never shows a broken image or a half-finished block. On localhost it shows a placeholder
> listing the files that are still missing.

## How it works

- **Download counting**: `total = direct from this site (D1) + GitHub release asset downloads (GitHub API)`
  - This site: `/download?variant=…` atomically increments that variant's `direct_<variant>` row
    in D1, then streams the artifact from R2. The top-level `direct` is the sum across variants;
    `variants` carries the per-variant breakdown.
  - GitHub: `/api/stats` fetches the GitHub API from Cloudflare at most once every 15 minutes and
    persists the result into D1 as a fallback. If GitHub is unreachable it keeps the last known
    value and never blocks the page.
- **An unknown variant is a 404**, not a silent fall back to the default — getting a file back
  from a typo'd parameter would fool you into thinking the parameter worked.
- **The artifact is checked before the counter is incremented**: otherwise, in the window between
  deploying the site and uploading the installers, every empty click would inflate the count.
- Artifacts are not public static assets, so `/assets/*.exe` 404s and nobody can bypass the count.
- `wrangler.jsonc` must keep `nodejs_compat` (the R2 streaming response needs `node:stream`).
- **Don't bump `compatibility_date` casually**: the workerd bundled with your local wrangler
  refuses dates newer than itself, and the symptom is that `pages dev` simply won't start.

## Adding another software

All of the backend (download counting, version, GitHub stats) lives in `functions/`. Adding a
new software **requires no new Cloudflare database or bucket**.

### 1. Copy the directory

In a new repository, copy `functions/`, `_headers`, `wrangler.jsonc` and `tools/`
(replace `index.html` / `assets/` with the new software's landing page).

### 2. Edit `functions/_lib/site.js`

```js
export const SITE = {
  app: 'newsoftware',                    // unique id: D1 app column + R2 directory prefix
  githubRepo: 'Tinger-X/newsoftware',    // for counting release asset downloads
  namePrefix: 'NewSoftware-',            // release filename prefix, used to parse the version
  ext: 'exe',                            // exe / apk / zip / dmg …
  contentType: 'application/vnd.microsoft.portable-executable',
  variants: [
    { id: 'default', counterKey: 'direct_default', bytesHint: 0 },
  ],
};
```

> Never change `app` once it is live: you would lose the historical counts and stop finding the
> artifacts already uploaded. With a single artifact, leave one entry in `variants`.

### 3. Create the Pages project and deploy

```bash
# change name in wrangler.jsonc to the new project
wrangler pages deploy --project-name=newsoftware
```

Keep the shared `database_id` / `bucket_name` as they are. The D1 table needs no rebuild —
counter rows are created automatically on the first download.

### 4. Upload the first artifact

```bash
wrangler r2 object put softwares/newsoftware/default.exe \
  --file <path> --remote \
  --content-type application/vnd.microsoft.portable-executable \
  --content-disposition 'attachment; filename="NewSoftware-1.0.0-default.exe"'
```

`/api/stats` then returns `{ direct: 0, github: <n>, total: <n>, version: "v1.0.0", variants: {…} }`.

### Wiring up the front end

The page only has to fetch `/api/stats` for `total`, `version` and `variants.*`, and point its
download buttons at `/download?variant=<id>` — see `loadStats()` in `assets/script.js`.
